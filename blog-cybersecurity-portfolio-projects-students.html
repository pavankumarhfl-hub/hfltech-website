CYBERSECURITY · STUDENT GUIDE

Cybersecurity portfolio projects that stay on the right side of the law

A strong security portfolio demonstrates method, evidence and restraint. Use systems you own or have explicit permission to test, and make defensive outcomes easy to review.

1. Build a home lab

Use isolated virtual machines or deliberately vulnerable training applications. Document the network boundaries, reset process and the scope of permitted testing. Never scan or exploit third-party systems without explicit authorisation.

2. Write a threat model

Choose a small application and identify assets, trust boundaries, entry points, likely threats and mitigations. A simple diagram plus a prioritised risk register can demonstrate practical thinking better than a long list of tools.

3. Review code for common weaknesses

Use a sample application or your own repository to demonstrate input validation, access control, secrets handling, dependency hygiene and secure error handling. Explain each finding, its impact and a test that verifies the fix.

4. Analyse sample logs

Use synthetic or lawfully obtained sample logs to create a small detection or alerting workflow. Include assumptions, false positives, sample events and the steps an analyst should take next. Avoid collecting personal data unnecessarily.

5. Create an incident response runbook

Write a clear playbook for a scenario such as a leaked test credential or suspicious login. Include triage, containment, evidence preservation, escalation, recovery and post-incident learning. Do not publish real secrets or sensitive incident details.

6. Demonstrate responsible disclosure

Learn how to report a vulnerability privately, provide reproducible steps within authorised scope, minimise data access and allow the system owner to respond. Do not access, alter or exfiltrate data to prove a point.

Present evidence, not just claims

Include a concise README, scope statement, setup instructions, screenshots with sensitive data removed, test results and limitations. Never include credentials, private logs or proof-of-concept material that enables harm against real systems.
