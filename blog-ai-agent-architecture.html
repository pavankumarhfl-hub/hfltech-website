AI agent architecture: from a model to a reliable system

An AI agent is not just a prompt. It is a system of reasoning, tools, state, permissions, evaluation and feedback.

← HFL Tech Journal

Students often begin building agents by connecting a language model to a tool and asking it to complete a task. A useful prototype can emerge quickly, but reliability requires a broader design. The model is one component; the surrounding system determines what it can access, what it is allowed to do, how errors are detected and when a person must intervene.

1. Define a bounded task

Start with a specific job, such as classifying support requests, summarising a set of documents or preparing a draft report. Define inputs, expected outputs, failure conditions and what success means before selecting a model. A narrow evaluation target is more useful than a vague claim that an agent is intelligent.

2. Separate the core components

  • Model: interprets context and proposes a next step.
  • Tools: perform explicit operations such as searching, calculating or reading an approved data source.
  • State and memory: retain only the information needed for the current task or a justified future interaction.
  • Orchestrator: controls the loop, tool routing, timeouts, retries and stop conditions.
  • Evaluation and logs: make quality, failures, latency and cost observable.

3. Treat tool permissions as a security boundary

Give each tool the minimum permissions needed. Read-only access should be the default when possible. Validate arguments, restrict file and network access, protect secrets, and require confirmation before consequential actions such as sending messages, changing records or making purchases. Content retrieved from documents, websites or emails should be treated as untrusted data—not as instructions that can override system policy.

4. Make state explicit

Do not rely on an ever-growing conversation history as the only memory strategy. Define which facts belong in temporary task state, which can be retrieved from an approved source, and which should never be retained. Provide deletion and correction paths where personal data is involved.

5. Evaluate more than the happy path

Build a representative test set. Include ambiguous requests, missing information, malformed tool results, prompt injection attempts, unavailable services and requests outside the agent's authority. Track task success, factual accuracy, tool errors, unsafe actions, latency and cost. Compare changes against a baseline before deployment.

6. Keep humans in control

Use approval gates for high-impact actions, show the user what will happen, and make cancellation possible. A robust agent should fail safely when confidence is low or required evidence is missing.

A practical student project

Build a document research assistant that searches a small, curated collection, quotes source passages, links every factual claim to its source, and refuses to answer when evidence is absent. Add tests for unsupported claims and malicious instructions inside documents. This project demonstrates more engineering maturity than a flashy demo without evaluation.
